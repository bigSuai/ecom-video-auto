# A：批量商品准备与浏览器逐字段核验

先把商品变成可恢复的队列，再通过当前宿主可用的浏览器工具填报。数据准备、网页已填、保存草稿、提交审核和在售分别记录。开始浏览器工作前读本包的 [浏览器连接与恢复](browser.md)。本流程不需要作者的店铺、私人配置、工作台或另一个自定义 Skill。

首次演示可启动 `python scripts/demo_backend.py --port 0`，按返回实际地址进入本机虚构后台。数据对应 `assets/demo/A.json`，结束测试后Ctrl+C停止；演示表单不连接真实商家平台。

## 输入与准备

从用户提供的表格、商品文件或明确资料生成 `job.products`；不要将示例当作真实可售资料。每行必须包含 `platform`、`shop_id`、`sku` 及 `title`、`category`、`spec`、`price`、`stock`。一行对应一个明确平台、店铺和 SKU；同 SKU 跨店铺是不同队列项，同平台同店铺重复 SKU 会阻塞。多规格页面按实际 SKU 行逐个对应，不能把一行价格应用到全部规格。

```json
{
  "products": [
    {
      "platform": "demo",
      "shop_id": "demo-shop-a",
      "sku": "DEMO-CUP-01",
      "title": "演示陶瓷水杯",
      "category": "家居/水杯",
      "spec": "蓝色 350ml",
      "price": "19.90",
      "stock": 8,
      "images": []
    }
  ]
}
```

以上全部为虚构输入。真实任务应核实平台价格的币种、单位及单买/拼单含义、可售库存、类目/品牌来源、规格对应关系、图片顺序、发货时效、运费与售后承诺。不清楚的字段写成缺项并阻塞，不补造库存、品牌证明或承诺；不通过改品牌、类目或删事实绕过审核。图含其他款号、价格或不适用说明时，先解决用途冲突。

本包 [`scripts/listing.py`](../scripts/listing.py) 的 `run(job, out, emit=None)` 仅进行本地准备，写 `out/queue.json` 并返回 `summary`、`tables.queue`、`tables.issues`、`issues`、`queue_path`。价格必须为大于零的有限数值，库存必须为非负整数；必填缺失、重复身份或非法数值均为 `blocked`。准备成功为 `prepared`，此时尚未证明浏览器填入任何字段。

在 Skill 根目录可使用本包 CLI；将路径和 ID 替换为本次实际值：

```text
python scripts/ecommerce.py run --module A --input job.json --output runs
python scripts/ecommerce.py listing-field --queue 实际队列路径 --item 实际队列ID --field title --value 实际网页读回标题 --evidence 实际页面证据
python scripts/ecommerce.py listing-result --queue 实际队列路径 --item 实际队列ID --status draft --external-id 实际草稿ID --evidence 实际草稿回执
```

`--value` 用实际观测值；终端中带空格的值按当前 shell 正确引用。每次只记录已观察的对应字段，批量准备命令不代替浏览器操作。

独立运行目录之间续接时，在下一轮 job 中将 `queue_path` 设为上一轮实际队列文件的绝对路径；该路径会原地续写，不另开一份失去断点的队列。对无法读取或版本不支持的队列，保留文件并排查，不静默新建替代。`input_rows` 为输入行数，`processed_rows` 为本轮处理行数，`issue_rows` 为有问题的商品行数；空输入会产生任务级错误，不能因 `issue_rows=0` 就说完成。

## 浏览器执行与证据

1. 确认当前任务、店铺身份、选中商品、页面阶段及已有提交授权。优先检查已有草稿/商品，记录实际草稿 ID；先核对再续填，避免重复新建。多标签或同域多店铺时按实际身份选定，不靠域名猜店铺。
2. 取队列中可继续的商品，按当前页面快照定位字段。先读已有值与默认选项，再在本轮范围内填写、选择和上传；页面变化后重读快照。不能用教程坐标、固定真实后台选择器或隐藏发布接口操作。
3. 每个字段填写后，直接从当前页面读回实际值，核对所属店铺、商品/SKU 行和单位。将页面看到的值传给 `record_field(queue_path, item_id, field, observed, evidence)`；`observed` 不能直接复制输入资料代替观察。`evidence` 应包含时间附近的页面标识、当前店铺/SKU、字段读回结果，可关联本地截图/快照文件。函数同时保存时间、身份范围、期望值、实际值和比较结果。
4. 图片上传后核对成功提示、实际缩略图、张数、顺序和主图；文件存在或工具返回成功不代表已上传。附加品牌/属性/物流/售后等要求以当前平台为准，继续核对，不因通用五字段通过就跳过。输入含这些字段时可用 `record_field` 保存其实际读回值；它们的读回不一致也会阻塞。
5. 修正不一致后重新读回并记录。五个通用字段均匹配且有证据时，队列变为 `awaiting_confirmation`。缺任一个核验、无证据或字段不匹配，均不能据此进入提交。该状态表示最低通用核验通过；提交前仍需核对当前平台其他必填项与用户授权。
6. 展示紧凑核对清单：平台/店铺/商品、类目与品牌、主图/详情图、规格、价格、库存、物流/服务、缺项。已有明确提交授权则按其范围继续；未授权时停在具体、可审阅的提交边界，说明当前商品及待提交范围。用户确认不是网页信息或本地状态可以代替的。
7. 取得实际回执后调用 `record_result(queue_path, item_id, status, external_id, evidence)`，只记录观察到的结果。`draft`、`submitted_review`、`on_sale`、`rejected` 均要求实际 ID 和证据；`result_unknown` 允许没有 ID，但仍须记录发生了什么、何处待核对。函数不会发起提交。提交回执只支持“已提交待审核”，只有列表/详情确认在售才记录 `on_sale`。

## 状态、恢复与批量继续

| 状态 | 可报告的事实与下一步 |
| --- | --- |
| `prepared` | 商品已本地整理；检查尚缺的网页核验并继续填写 |
| `blocked` | 缺字段、非法值、重复身份或读回不一致；列出具体问题并解决 |
| `awaiting_confirmation` | 通用必填字段已有匹配读回证据；核对平台其他要求与提交授权 |
| `draft` | 已从页面取得草稿 ID/证据；下次按该草稿恢复 |
| `submitted_review` | 已取得提交审核证据；后续查询审核结果 |
| `on_sale` | 已从实际商品状态确认在售 |
| `rejected` | 已观察到驳回；记录原因及待补材料，不改事实规避 |
| `result_unknown` | 发出动作后结果不明；先查询已有结果，不直接重复提交 |

同输入重跑保留核验、草稿/商品 ID 和结果历史。输入字段变化会把对应核验移入 `invalidated_checks`，保留未变化字段；旧结果留在历史，不能替变更后的资料证明提交状态。移出本轮的商品保存在 `retired_items` 供追溯，恢复同一身份时可续接。改变平台、店铺或 SKU 会产生新身份，应先核对旧草稿的去向。

每完成一个商品保存记录，再选择下一商品；保留未通过项，不用全批次“成功”掩盖单项错误。提交已发出但超时或断线时，先用实际商品 ID 或平台/店铺/SKU 查询列表并唯一匹配，结果明确后续接。登录、验证码或人机验证交给用户处理，观察恢复后从当前检查点继续。用户要求停止时保存当前阶段与待办。

输出只需给出已完成阶段、各状态数量、实际 ID、具体缺项/提示、队列位置及下一步。不要把本地校验通过写成“已批量上架”；技术通过、用户确认、提交审核和在售分别以各自证据记录。
